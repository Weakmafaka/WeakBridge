# WeakBridge — план развития одного приложения на часах

**Дата:** 2 ноября 2026 года. **Отправная версия:** 0.1.4. **Текущая версия:** 0.2.0.

## 1. Идея продукта

Одно устанавливаемое приложение на уже настроенных Wear OS-часах. Оно напрямую соединяется с iPhone по Bluetooth, показывает разрешённые уведомления и управляет воспроизведением музыки. На iPhone используются встроенные системные сервисы ANCS и AMS и обычные настройки Bluetooth.

Для ежедневной работы не требуются iOS-приложение, аккаунт WeakBridge или сервер. Экраны приложения, фоновая служба, Tile и complications поставляются внутри одного APK. Установка APK через компьютер допустима; первоначальная настройка самих часов остаётся предварительным условием.

Этот документ объединяет только функции и технические решения, соответствующие такой архитектуре. Он описывает план разработки, а не обещает наличие всех перечисленных функций в версии 0.1.4.

Разделы 2–10 описывают исходный объём и направления развития. **Текущее состояние реализации 0.2.0 находится в таблицах раздела 11**; исходные пометки «Добавить» выше не заменяют эти таблицы.

**Статусы:**

- **Есть:** механизм найден в текущем коде WeakBridge; полная аппаратная проверка может быть ещё не проведена.
- **Добавить:** функция реализуется на часах с использованием описанных API.
- **По возможностям:** интерфейс включается только при наличии поддержки у iPhone, плеера или часов.

## 2. Сопряжение и соединение

| Функция | Статус | Реализация |
|---|---|---|
| Сопряжение из Bluetooth-настроек iPhone | Есть | Пользователь открывает ограниченное окно видимости на часах и подтверждает системные запросы |
| Явный выбор сохранённого iPhone | Есть | Выбор OS bond; имя устройства не используется как единственное доказательство его идентичности |
| Сохранение выбранного устройства | Есть | Настройки часов содержат ссылку на выбранное сопряжение |
| Работа после закрытия экрана приложения | Есть | Foreground service типа connectedDevice |
| Ограниченное автоматическое восстановление | Есть | Задержки с увеличением интервала и jitter, затем пассивный autoConnect |
| Восстановление после загрузки часов | Есть | Учитывает разрешения и настройки пользователя; требуется проверка по прошивкам |
| Обработка появления/исчезновения ANCS/AMS | Есть | Service Changed и пересоздание подписок |
| Понятный мастер подключения | Добавить | Отдельные шаги: разрешения часов, сопряжение, выбор iPhone, доступ к уведомлениям, готовность музыки |
| Экран состояния | Добавить | Показывать отдельно Bluetooth-соединение, доступность ANCS, AMS, разрешения и последнюю причину ошибки |
| Восстановление вручную | Есть; улучшить пояснения | Повторное соединение с выбранным iPhone без повторного сопряжения |

Главный путь первого подключения — запрос видимости часов и Bluetooth-настройки iPhone. Поиск ANCS остаётся дополнительным инструментом: iPhone не обязан рекламировать этот сервис в сканировании.

**Критерии готовности:** повторное подключение к тому же телефону, отсутствие одновременных GATT-клиентов, корректное поведение после выхода из зоны связи и переключения Bluetooth. Ошибка разрешения должна отличаться от отсутствия сервиса на телефоне.

## 3. Уведомления

### 3.1. Получение и жизненный цикл

**Есть:** новые ANCS-уведомления, обновление и удаление по UID, получение текста и app identifier, фильтр категорий, пропуск старых уведомлений при подключении, ограниченные очереди и действия, объявленные iOS.

**Доработать:**

1. Согласовать число опубликованных уведомлений с системным пределом. Сейчас WeakBridge допускает 100, тогда как в AOSP Android 13 установлен предел 50 на приложение. Оставлять запас для уведомления службы, плеера и групп; конкретное поведение Samsung проверить отдельно.
2. При большом потоке объединять ещё не обработанные изменения одного UID и вытеснять старые записи по понятной политике.
3. Не допускать появления удалённого уведомления после завершения отложенного чтения.
4. Публиковать обновление существующего сообщения без повторного звука и вибрации.
5. Проверить системные ANCS-флаги тихих и важных уведомлений и соответствие локальной политике оповещения.
6. Сохранять реальные новые сообщения сразу после reconnect. Общий запрет уведомлений на первую минуту не нужен.

### 3.2. Настройки и оформление

| Функция | Статус | Детали |
|---|---|---|
| Фильтр по категориям | Есть | Пользователь выбирает категории на часах |
| Фильтр по приложениям | Добавить | Список формируется из полученных app identifier; выбор хранится локально |
| Названия и иконки приложений | Добавить | Локальные сопоставления, кэш имён из ANCS, нейтральный fallback неизвестным приложениям |
| Группировка | Добавить | По приложению с ограничением числа элементов и корректной очисткой группы |
| Тихие часы | Добавить | Локальное расписание сигналов на часах |
| Настройка повторных сигналов | Добавить | Ограничение частоты вибрации при всплеске, сохранение самих сообщений |
| Раздельные каналы | Добавить | Звонки, сообщения и другие категории с пользовательскими настройками Android |
| Скрытие содержимого | Есть частично; расширить | Private visibility, выбор показа только отправителя/приложения, учёт доступных на iPhone превью |
| Действия уведомления | Есть / по возможностям | Показывать только positive/negative, разрешённые iOS; использовать предоставленные подписи |

Иконки нужно поставлять с разрешённой лицензией. Наличие локальной иконки не означает, что соответствующее iPhone-приложение установлено на часах.

**Важное ограничение фильтра:** app identifier обычно становится известен после запроса атрибутов. Фильтр на часах уменьшает отображение и сигналы, но сам по себе не останавливает передачу всех исходных ANCS-событий с телефона. Кэш для уже известных UID и ранний отсев категорий могут сокращать дальнейшую работу.

### 3.3. Необязательная история на часах

**Добавить как отключаемую функцию:**

- Сохранять только уведомления, которые действительно получил WeakBridge.
- По умолчанию оставить текущее хранение содержимого в оперативной памяти.
- Для постоянной истории предусмотреть согласие, ограничение объёма/срока, очистку и защиту хранилища.
- Отдельно показывать время получения часами. Исходное время iPhone отображать только при наличии соответствующего ANCS-атрибута.
- При удалении истории удалять связанное содержимое; диагностический журнал текста сообщений не содержит.

Это история полученных событий, а не доступ ко всему архиву уведомлений телефона.

## 4. Музыка и управление воспроизведением

**Есть:** MediaSession, MediaStyle-уведомление, название, исполнитель, альбом, длительность и состояние из AMS; play/pause, следующий/предыдущий трек и относительная громкость. При смене номера трека сохраняется состояние сессии, а устаревшая позиция помечается неизвестной.

### Расширение управления

| Функция | Статус | Реализация |
|---|---|---|
| Собственный экран плеера | Добавить | Метаданные из существующего AMS state и команды через текущую очередь |
| Кнопки на Tile | Добавить | Play/pause, next/previous, переход к плееру |
| Быстрый доступ с циферблата | Добавить | Complication со статусом и переходом в приложение |
| Shuffle и repeat | По возможностям | AMS-команды 8 и 7, состояние режимов из Queue attributes |
| Пропуск вперёд/назад внутри записи | По возможностям | AMS-команды 9 и 10; величину шага определяет плеер |
| Like/dislike/bookmark | По возможностям | AMS-команды 11–13 |
| Управление громкостью из собственного экрана | Добавить / по возможностям | Те же относительные команды AMS |
| Поворот безеля в собственном плеере | По возможностям часов | Обработка rotary input видимого экрана и отправка поддержанной команды |
| Корректная смена плеера | Есть основа; проверить | Сброс данных предыдущего приложения, актуальный набор команд и новые атрибуты |

**Правила реализации:**

- Доступность каждой кнопки определяется актуальным support set от iPhone.
- Команды просрочиваются и отбрасываются после разрыва; на новом соединении не воспроизводятся.
- Для времени воспроизведения использовать настоящие данные AMS и системную экстраполяцию. Локальную анимацию позиции включать только для видимого экрана.
- Повторно публиковать метаданные и уведомление только при изменении соответствующего содержимого.
- Восстановление пропущенных метаданных ограничить числом попыток; не добавлять бесконечный таймер проверки.
- Графические элементы плеера поставлять локально. Обложки не требуются для работоспособности.

Интеграция с системным контроллером Samsung проверяется отдельно от собственного экрана. Стандартная MediaSession даёт путь интеграции, но не гарантирует одинаковое поведение каждого циферблата и прошивки.

## 5. Входящие звонки через уведомления

Реализуемый объём — отображение ANCS-события звонка и действия, которые iOS предоставил этому событию.

**Добавить:**

1. Отдельную карточку входящего звонка с доступным именем/номером и источником.
2. Быстрое отображение минимальной карточки при достоверной категории IncomingCall; уточнение текста после получения атрибутов.
3. Кнопки по актуальным action flags и подписям ANCS.
4. Ограниченную длительность повторной вибрации.
5. Немедленную отмену сигналов при удалении события, разрыве связи или выполнении действия.
6. Защиту от повторного открытия экрана для одного звонка.

Не делать слово «звонит» в произвольном сообщении единственным основанием для звонкового интерфейса. Это снижает ошибки языка и ложные срабатывания. Состояние «звонок принят» показывать только по подтверждённому событию, а не по одному нажатию кнопки.

Эта карточка управляет уведомлением; голосовой аудиоканал не входит в данный план.

## 6. Интерфейс одного APK

**Добавить:**

- Полную русскую и английскую локализацию.
- Главный экран с краткими состояниями связи, уведомлений и музыки.
- Мастер подключения и контекстные инструкции восстановления.
- Экран плеера, настройки приложений/категорий и диагностику.
- Tile для быстрых действий и complication для открытия приложения/статуса.
- Сдержанные локальные анимации только при взаимодействии с экраном.
- Корректное управление поворотом физического безеля, если он есть.
- Совместимость с системной навигацией и специальными возможностями.

Tile и complication не должны запускать постоянное сканирование, опрос или обновление раз в секунду. Быстрые действия должны корректно показывать отсутствие соединения и не запускать сопряжение без решения пользователя.

## 7. Необязательные локальные показатели здоровья

Этот модуль может находиться в том же APK и работать самостоятельно на часах.

**Допустимый объём:** шаги, доступные через Health Services дневные показатели и пульс при наличии поддержки и разрешений. Можно добавить локальную карточку и ограниченную историю. Перед подпиской нужно проверять возможности устройства; неподдержанные показатели скрывать.

**Технический подход:**

- PassiveMonitoringClient для фоновых данных вместо собственного частого опроса датчика.
- Фоновую подписку снимать при отключении модуля и отзыве разрешений.
- Обрабатывать пакетные значения с правильными timestamp и дневными границами.
- Сохранять/обновлять интерфейс пакетами, а не при каждом небольшом изменении.
- Модуль по умолчанию выключен, разрешения запрашиваются при его включении.

Это низкий приоритет относительно стабильности моста. В данный объём входят только локальные данные с публичным API; интеграция Samsung Health Sensor SDK и клинические измерения не требуются.

## 8. Экономия батареи

### Сохранить существующие решения

- Одно BLE-соединение и одна сериализованная очередь операций.
- События ANCS/AMS вместо опроса телефона.
- Ограниченные очереди, дедупликацию и проверку устаревших ответов.
- Пропуск PreExisting и отключённых категорий до запросов содержимого.
- Рекламу на 120 секунд и поиск на 20 секунд только по действию пользователя.
- BALANCED при настройке и LOW_POWER в простое по умолчанию.
- Ограниченные попытки восстановления с увеличением задержки и пассивным завершением.
- Максимум две попытки восстановления метаданных на соединение.
- Обновление медиасессии и уведомления только при значимых изменениях.
- Отсутствие постоянных wake lock, Wi-Fi lock, ADB-watchdog, heartbeat и сетевой аналитики.

### Добавить

| Работа | Ожидаемый механизм пользы | Как проверить |
|---|---|---|
| Ограничение повторных сигналов | Меньше вибрации и включений экрана при всплеске | Один и тот же поток уведомлений, число сигналов и задержки |
| Фильтры, кэш и объединение изменений UID | Меньше лишней обработки и повторных запросов | Число и объём GATT-операций на одинаковом потоке |
| Разумный бюджет уведомлений | Меньше системных отказов и лишних публикаций | Всплеск выше лимита, вытеснение и корректность новых сообщений |
| Объединение обновлений интерфейса | Меньше повторной работы при пакете метаданных | Частота setMetadata, setPlaybackState и notify |
| Управление нагрузкой экрана | Анимации и расчёт позиции только при видимости | Trace при открытом экране и после ухода в AOD |
| Короткие диагностические события | Установление причин расхода без постоянного таймера | CPU, размер журнала и отсутствие содержимого сообщений |
| Пассивные локальные сенсоры | Использование системного batching | Частота callback, регистрации датчиков, расход с модулем и без |

### Реализуемые эксперименты перед выбором настроек

**Приоритет соединения:** сравнить существующий LOW_POWER и BALANCED в сценарии активного управления музыкой. Если измерения подтвердят необходимость, сделать управляемый переход между режимами с возвратом в простой. Не менять приоритет на каждом пакете. Повышение приоритета — запрос контроллеру, а не гарантированная настройка радиоканала.

**MTU:** проверить однократное согласование при подключении. Это может позволить получать длинные имена приложений и уменьшить фрагментацию. На Android 14+ первый запрос заставляет stack запросить 517; реальное согласованное значение зависит от другой стороны. Результат оценивать по пакетам, задержкам и расходу, а не по величине MTU.

Оба эксперимента допустимы в одном приложении на часах. Процент экономии заранее неизвестен; экономичный режим по умолчанию меняется только после проверки.

## 9. Диагностика и приватность

**Добавить журнал без текста уведомлений:**

- Переходы между состояниями соединения и причины ошибок.
- Длительность поиска, соединения и восстановления.
- Количество GATT-операций, принятых/переданных байтов и таймаутов.
- Частоту AMS-обновлений и публикаций Android-уведомлений.
- Число вытесненных событий и отклонённых устаревших команд.
- Заряд при старте/конце пользовательского измерения.

История диагностики ограничена по объёму. Временные интервалы измеряются монотонными часами; календарное время используется для отображения. Идентификаторы устройства, сообщения, имена отправителей и музыкальные названия в экспорт не включаются. Экспорт запускается пользователем.

Счётчик callback не называется числом аппаратных пробуждений CPU. Значение батареи в процентах не выдаётся за точный замер потребления приложения.

- ⚪ **Не начато** — нового механизма, эксперимента или расширенной приёмки ещё нет.

Столбцы «Что уже есть» и «Доработка» показывают конкретный остаток работы. Для исследований отсутствие замеров означает «не начато», даже если переключатель режима уже существует. Выполненный релиз не означает, что все сценарии совместимости проверены.


Рабочий цикл: выбрать этап → проверить текущее поведение → внести изменение → выполнить подходящие проверки → записать результат и оставшиеся ограничения. Аппаратную проверку отмечать отдельно от JVM-тестов. На этапе исследования возможны решения «сохраняем текущую реализацию» и «откладываем: выгода не подтверждена».


**Сводка 45 этапов:** 5 выполнены для указанного объёма; 17 реализованы с неполной приёмкой; 10 частично; 13 ещё не начаты. Этапы разного размера; это не процент готовности.

## 12. Проверка батареи и совместимости

Начать с имеющегося комплекта Galaxy Watch6 SM-R930 + iPhone 13 / iOS 26.0. Аппаратно подтверждены сопряжение и базовое управление музыкой; остальные сценарии нужно проверять отдельно.

При одинаковых AOD, яркости, циферблате, Wi-Fi/LTE и сценарии сравнить:

1. Мост отключён.
2. Соединение без событий.
3. Фиксированный поток новых и изменённых уведомлений.
4. Музыка при погашенном интерактивном экране.
5. Музыка с переключением и регулировкой громкости.
6. Телефон вне зоны, затем возврат.
7. Bluetooth off/on и восстановление после загрузки часов.
8. Дополнительные локальные сенсоры отдельно от основного моста.

Wireless ADB выключать на разрядных прогонах; profiling с отладкой проводить отдельно. Повторять парные прогоны и чередовать порядок. Оценивать заряд, CPU/wakelock/radio time, объём GATT, задержки и потери. Отсутствие уведомлений из-за потерянного соединения не считается экономией.

После Watch6 расширять матрицу устройств. В карточке совместимости отдельно отмечать pairing, ANCS, AMS, системный плеер и дополнительные локальные возможности. Один успешный запуск не означает поддержку всех Wear OS-часов.
